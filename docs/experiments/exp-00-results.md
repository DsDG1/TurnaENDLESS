## 1. 结论摘要

**试跑阶段小结（20 批 × 10 次 + 6 批 × 4 次探针，提示词 v7→v12 + 机械修复 + 分阶段输出上限）**——正式判定要等 R0–R5 与人工评审，这里先记录已经能下结论的部分：

- **判定**：暂不判定（R0–R5 未跑，人工项未评）。试跑证据支持「继续做 MVP」，不支持「调整方向」或「停止」。
- **支撑证据**：最佳配置（v10/v11/v12 + 五类机械修复）三次采样 19/20、17/20、18/20，合计 54/60 = **90%**（§4.2），V2 阈值 97% **未达标**；同时 C1 **0.0%**（阈值 ≤2%，达标）、L1 **100%**（阈值 ≥90%，达标）；N2 需要第 21 批起才有定义，20 批样本不判；K2 因 `prices.yaml` 未填不可判定；L4/L5/N5/「想看下一张」为人工项。提示词矩阵（§4.4）同步从 1/10 → 5/10 → 8/10。
- **一句话结论**：真实模型的首轮输出几乎总有一处「声明了但没做到」——20 批里只有 2–3 批完全干净（**V0 = 10–15%**：v11 15%、v12 10%，v10 是 5%）。把「删声明 / 改展示字段」这类机械修复放到本地（五类，每次修正都打日志）、把「故事写坏了」留给 LLM 修复循环，能把 V2 推到 85–95%；剩下那几批是「模型编了一个名字」（不存在的素材、条目 id、背景标签），**提示词教不动**——列反例甚至会把不存在的名字直接喂给模型（§4.2 的 20n 小节），v12 删掉反例后模型照样自己编出来（20o 小节）。

## 4. 试跑观察（Day 8）

### 4.1 供应商与模型

- 供应商：OpenAI 兼容端点 `https://api.minimax.cn/v1`（写在 `config/models.yaml`）；key 只从环境变量 `ENDLESS_API_KEY` 读取，不写入任何运行文件。
- 两档模型都写在 `config/models.yaml`，目前**两档同为 `MiniMax-M3.1-Flash`**，且本实验**只用这一个型号**（2026-10-22 决定；高档位只是给将来换型号留的位置，见 §7 第 8 条）。该模型是推理模型：响应用 `reasoning_tokens` 单列思考量，**思考也计入 `max_tokens`**。
- `models.yaml` 因此显式设 `reasoning_effort: low` 与 `timeout_ms: 300000`。同一提示词下，`low` 把思考 token 从约 330 降到约 115（单次探针）；不提速时单次调用可到 80–100 秒。
- **思考关不掉是常态，不是例外**（2026-10 单次探针，3 组对照）：
  - `MiniMax-M3.1-Flash` + `thinking:{type:'disabled'}` → **HTTP 400**，报错原文 `model "MiniMax-M3.1-Flash" requires adaptive thinking; thinking.type="disabled" (including reasoning.effort=none) is not supported`。它只能调 `reasoning_effort`，**没有关掉思考的开关**。
  - 对照探针里另一个型号 + `reasoning_effort: low` → 思考被**内联进正文**（`content` 以 `Thinking:…` 开头，`reasoning_tokens=105`），同一写批任务 13.1s vs 4.0s；只有 `thinking:{type:'disabled'}` 才干净（4.0s）。即「关思考」是**逐模型能力**，不是通用参数。
  - 因此不赌「思考一定关得掉」：`models.yaml` 的两档都配 `MiniMax-M3.1-Flash`，并在**解析层**兜底——`packages/esl/src/parse.ts` 的 `stripThinking()` 会剥掉正文开头的内联思考块（`Thinking:…` / `<thinking>…</thinking>`，有闭合标记按标记切，没有则切到第一行像答案开头的行），`parseBatch()` 与导演的计划解析、评审的 JSON 解析都先过它。换更强的模型只改 `models.yaml`，不需要改代码。
  - 这一条推翻了两处早先的结论：旧版说「只有 `thinking:{type:disabled}` 能关掉」——那只对当时的型号成立，对 Flash 直接 400；`promptfoo` 那一节的「高档行测的是关掉思考的模型」也随之失效——现在高档就是 Flash。

顺带记一笔上限问题：`b-0009`、`b-0013` 各出现一次 showrunner `finish=length`（4096 全是思考、正文空），都被 `maxPrecheckRetries` 的预检重试救回（第二批 13.5s / 32.8s 正常返回），没有影响通过率，但这两次空转合计烧掉约 8k 思考 token——20h 把 showrunner 从 2048 提到 4096 之后，v10/v11 更长的提示词又把它顶到了边缘。

### 4.3 与 Stub 冒烟的差异

Stub 5 批（`pnpm lab smoke`）只能证明流水线接线正确：Stub 的 YAML 是人写的、必然合法。真实模型的差异集中在三处，且都在试跑第一小时内暴露：

1. **输出形状**：模型会发明字段。提示词里必须有可照抄的完整样例，散文式规范不够。
2. **输出预算**：推理模型的思考与正文共享上限，长输出任务必须单独放宽，否则表现为「空响应」而不是「截断报错」。
3. **修复循环的有效边界**：schema 级错误时解析不出批次，`badSceneIds` 为空，修复循环直接放弃（`repairRounds` 计数却已自增）。这解释了「记了 2 轮修复但一次 repair 调用都没有」的现象；提示词修好后修复轮次才真正用于语义级问题。

### 4.4 promptfoo 回归矩阵（2 模型 × 5 条样例）

- **证据等级写高是唯一贯穿两个模型、在五条样例里出现四次的一类，而它的根因在提示词自己身上**：v9 的 `single.md` / `writer.md` 示例里，`chat` 场景只给 3 个 `reply.options` 却标着 `recognition-4`，而校验器只在恰好 4 个选项时才推导出 `recognition-4`（`deriveEvidenceType`）。提示词的示范与校验器冲突，模型照抄范例就是错——§4.2 的 `E-EVIDENCE-OVERCLAIM` 与 20k 里 6 次 `[autofix] premature-evidence` 都属于这一类。v10 改掉示例（补第 4 个选项）并补一条硬规则，见 §5 第 5 条；**v11 重跑后这一类归零**。
- `@emoji:hat` 这一格要打折看：`hat` 在 brief 的 `allowed_extra` 里，它是**词**不是素材名（清单里只有 `top_hat`）。模型把「允许的词」当成「允许的素材」，夹具确实给了这层诱导；`@emoji:book` 没有诱导，是纯模型错误。v11 重跑里 `@emoji:hat` 仍出现 2 格，说明这层诱导是夹具的固有噪声，不是提示词能修的。
- 两个模型**不是同一个失败谱**：快速档错在 schema / 属性（`effects` 形状、表情表、未声明的 cast），高档错在语义声明（证据等级、`uses`）。所以「换个更强的模型」不会同时修好两类，这也是流水线保留机械修正 + 修复循环的理由。
- **矩阵的 1/10（v9）与 5/10（v11）都不与流水线的 V2 90% 矛盾**：矩阵量的是**首轮单次生成、不修不重试**，流水线量的是**修复之后**；两者量的不是同一件事（V0 指标也是这个意思）。矩阵分数也不能直接和 V0 比大小——判据更松，见下面「矩阵与 V0 不是一把尺子」。

**v12 重跑（同一份矩阵，只换提示词版本；v12 = 删掉两个字面量非法标签 + 补道具正例清单）**：

| 样例 | 快速档 | 高档 |
|---|---|---|
| duck_detective / A1 / 位置介词暴露 | ✅ | ✅ |
| duck_detective / A1 / 到期复习（ck:where-is） | ✅ | ✅ |
| impossible_store / A1 / 价格词块 | ✅ | ✅ |
| impossible_store / A2 / 到期复习（ck:how-much） | ✅ | ❌ `E-USES-NOT-FOUND@s2`：`uses` 声明了 `lx:borrow#v.take-temporarily`，正文里没有 |
| improv / A1 / 纯暴露 | ✅ | ❌ `E-USES-NOT-FOUND@s3`：`uses` 声明了 `ck:do-you-have`，正文里没有 |

- 合计 **8/10 通过（80%）**，3 分 25 秒、44 693 token，**0 格基础设施错误**（v11 有 1 格 529）。
- **`@emoji:hat` 两格全消失**（v11 是 2 格失败），快速档 **5/5 第一次全过**。这正是 v12 那行正例清单的目标：`hat` 在 `allowed_extra` 里是**词**、素材清单里只有 `top_hat`，给它一个能直接抄的名字，比在提示词里解释「`hat` 不是素材」有效。**这是本轮唯一被证实的收益**。
- `E-EVIDENCE-OVERCLAIM` 继续 0 格（v9 的 5 格已连续两轮归零），说明 v10 的修法稳定。
- 剩下的 2 格全是**高档模型**的 `E-USES-NOT-FOUND`（声明与实际不符）——和 20 批跑批里的失败谱同构：模型愿意「声明学会了」，但正文没写。这一类流水线里靠 autofix `s3`（删掉文本里找不到的 `uses`）修，矩阵里不修，所以矩阵分数天然低于 V2。
- 三轮矩阵的走势（1/10 → 5/10 → 8/10）跨越了 v9→v12 四次提示词改动，**每格只有 1 次采样**，只能当方向看。

**矩阵与 V0 不是一把尺子（8/10 与 V0 10–15% 的落差从哪来）**

矩阵断言走的是 `pnpm lab assert`（`promptfoo/esl-assert.js` 只负责把输出喂进去），而 `cmdAssert` 构造的校验上下文比流水线**松得多**：

| 判据 | 矩阵（`lab assert`） | 流水线（V0 / V2） |
|---|---|---|
| cast 实体是否存在 | `entities.exists` 恒真 ⇒ `E-ENTITY-UNKNOWN` 只剩「说话者不在批次 `cast` 里」这一种 | 查 `new_entities` 与角色规格表，编出来的角色会阻断 |
| 世界状态 | `canonFacts` / `activeFacts` / `threads` 全空 | 真实 canon + 活动事实 + 伏笔台账，`E-EFFECT-*` / 矛盾检查全开 |
| 允许词表 | 整本词库 + 功能词 + 专名 + `allowed_extra`，**不走能力门** | `knownWordSet(ability ≥ 0.6)`，比矩阵窄一个量级 |
| brief 覆盖（L1） | 不检查（没有 brief） | `E-BRIEF-UNCOVERED` 会阻断 |
| 生成形态 | `single.md` 单段、一个批次、一次调用 | 两段式、3–4 卡多场景、含重写 |

所以 8/10 与 V0 10–15% 之间的落差**大部分是判据不同**，不是模型在矩阵里表现更好。矩阵的用途只有一个：同一份判据下**纵向**看提示词改动有没有回退（1/10 → 5/10 → 8/10），不要拿它和流水线指标互相换算。

**适配层的两个坑（都已固化进 `promptfoo/provider.js`）**

1. promptfoo 0.124 的 `openai:chat:` provider **不透传 `config.reasoning_effort`**（该参数只在 abliteration / openrouter 等少数 provider 里实现）。推理模型的思考与正文共享 `max_tokens`，结果 10 格全部 `finish_reason=length`、输出以 `Thinking:` 开头、`0 passed / 5 errors`，两次共烧掉约 10 万 completion token。改成 30 行自定义 provider（`file://provider.js`，自己 POST `reasoning_effort`）后一次通过解析。
2. 对照探针里另一个型号把思考**内联进 `content`**（`Thinking:…` 前缀，没有单独的 `reasoning_content` 字段）；`reasoning_effort: minimal` 与 `enable_thinking: false` 都无效，只有 `thinking: {type: disabled}` 能关掉。**但这条不能推广成「思考总是关得掉」**：`MiniMax-M3.1-Flash` 对 `thinking: {type: disabled}` 直接返回 HTTP 400（`requires adaptive thinking`），即 Flash 档根本没有关思考的开关。所以矩阵不再赌「关思考」——`models.yaml` 两档都用 Flash，解析层用 `stripThinking()` 兜底内联思考（§4.1）。

**样例夹具的四个坑**（前两个早已固化，后两个这次才踩到）：

1. `char_specs` 必须带真实表情/配件表，否则模型写出 `expr=serious` 这类不在表里的表情 → `E-CHAR-ATTR`。
2. `asset_tags` 必须是 `data/assets/manifest.yaml` 里真实存在的背景标签与 emoji 名（背景只有 6 个，`@tag:street` 直接 `E-ASSET-MISSING`；`hat` 是 tag 不是 emoji 名）。另外 `lab assert` 有 `--oov-warn` / `--oov-block` / `--allowed-extra`，矩阵按运行配置的 8%/25% 与用例词表判定，否则默认 2%/5% 会把「能过流水线」的批次判成失败。
3. **占位符漏填**：`single.md` 有 16 个占位符，`defaultTest.vars` 原来只给了 9 个，`backgrounds`（v9 新增）/ `learning_checklist` / `allowed_words` / `retry_note` 一直以字面量 `{{...}}` 送进模型。之前那版「3/10」就是在提示词缺这四块上下文时量出来的，不能当基线。现已补上：`backgrounds` 与 `allowed_words` 由 `promptfoo/render-vars.ts` 按流水线 `buildVars` 的同一规则算出（冷启动、A1 的真实允许词表），脚本带 `--check` 防止以后再漏。
4. **夹具里自造了词库条目**：A2 样例的 brief 曾写 `lx:cheap#adj.affordable`，真实条目是 `lx:cheap#adj.inexpensive`，模型老实照抄 `uses` 就触发 `E-SCHEMA`。夹具引用的每个 `lx:` / `ck:` id 都必须能在 `data/lexicon` 里查到——这一条同样是矩阵可信度的前提。

### 4.5 「重写净效果」首测（6 批探针 → 20 批复测）

§7 第 6 条要回答的是「修复循环会不会越修越差」。为此导演从第一次校验起就留存首版问题单（`firstDraftIssues`），`report.json` 与失败批次的 `failed.json` 都写，`metrics.json` 聚合成 `rewriteEffect`。为了验证这条链路在真实失败批次上真的有数，跑了一次 6 批探针 `fd-probe6`（`config/run-fd-probe6.yaml`，除 `run_id` 与批数外与 20n 完全一致，所以前 6 批与 20n 的前 6 批同源）。

| 项 | 值 |
|---|---|
| 通过 | 6/6，23 卡，21 次调用 |
| V0 原始首轮零错误 | 2/6 = 33.3% |
| V1 机械修复后首次通过 | 4/6 = 66.7% |
| V2 修复后通过 | 100% |
| 首版即有阻塞错误 | 2 批 → 救回 2、丢掉 0 |
| 首版干净却最终失败 | 0 |

两个带阻塞错误的批次走了**两条不同的救回路径**，正好说明这个指标为什么必须分字段记：

- `b-0004`：首版只有 1 个 `E-ASSET-MISSING`，autofix / 逐场修复就地改掉，最终 0 错误——机器修得动的那类。
- `b-0006`：首版自造了两个 cast 成员（`robot`、`clerk`），连带 6 个阻塞错误（`E-ENTITY-UNKNOWN` ×2 + `E-ASSET-MISSING` ×4）；autofix 不敢猜角色，整批重写一次后干净，只剩 `W-OOV 13.1%`。**这正是「模型编名字」那一族里唯一能靠重写救回来的分支**，也解释了 §4.2 里 20n 那 2 批为什么失败：它们是在重写**之后**才写出非法条目 ID 的。

必须说清楚的分寸：6 批的噪声是 ±2 批，33.3% 的 V0 不能拿去和 20 批的 15% 比大小；这一节的结论只有一条——**链路通了，且救回/丢掉/改坏三类能分得开**。

**20 批复测（`smoke-real-20o`）**：首版带阻塞错误 7 批 → 救回 5、丢掉 2、**改坏 0**。这是第一次在 20 批规模上看到「零改坏」，而 20n 的 2 批是重写之后才失败的。丢掉的两批（`b-0008` 的 `mouse` 自造 cast + `@tag:apartment`、`b-0010` 的 `lx:mouse#n.rodent` 未覆盖）都是重写两轮也修不了的名字类——**重写能救「结构」，救不了「名字」**，这与 §4.2 的失败谱一致。

两处口径细节要写进这里，否则数字会被误读：

- `firstDraftIssues` 取的是**第一次尝试**的问题单，解析失败的那次也算。所以「首版带阻塞错误 7 批」里混着一条**不是重写救回来的**：`b-0003` 首轮因为 4 个非法条目 ID 被 zod 拒掉（`E-SCHEMA`），解析重试后一次通过、`repairRounds=0`，它在 `rawFirstPass` 里是 `true`（`rawFirstPass` 只看第一个**解析成功**的版本）。也就是说 `recovered` 同时包含「解析重试救回」与「修复循环救回」两条路径，目前没有分列。
- 因此 `rawFirstPass`（首个可解析版本是否零错误）与 `firstDraftIssues`（首次尝试是否有问题）**量的不是同一个瞬间**，不要互相对账；前者是 V0 的口径，后者是重写账的口径。

### 4.6 词库扩容实测（62 → 143 条：6 批探针 + 20 批复测）

偏差 #1 与 §7 第 3 条都把 L3 的 13% 归因于「词库只有 62 条」。这条判断被这一轮实测推翻了。词库扩到 **143 条（106 词义 / 22 词块 / 15 句型）**、功能词 226 → 321，再用同一把尺子复测：

| 运行 | 词库 | L3 中位 | L3 P95 | 不同生词 |
|---|---|---|---|---|
| `smoke-real-20n`（20 批） | 62 条 | 13.5% | 24.4% | — |
| `fd-probe6`（6 批） | 62 条 | 11.5% | 13.1% | — |
| `lex6`（6 批） | 143 条 | 12.1% | 16.4% | 19 |
| `lex6b`（6 批，口径修正后） | 143 条 | **9.8%** | 16.9% | 21 |
| `smoke-real-20o`（20 批，口径修正后） | 143 条 | **9.7%** | 18.9% | — |

三份配置除 `run_id` 与批数外完全一致，OOV 阈值都保持放宽后的 8%/25%，所以 L3 横向可比；但 6 批的噪声是 ±2 批，**这两组只读 L3，不读通过率**（`lex6` 5/6、`lex6b` 5/6 是副产品）。作为量级参照：扩表前的 20 批运行里累计出现过 411 个不同生词，扩表后的 6 批探针只有 19–21 个。`20o` 是**扩表后第一个 20 批样本**（修正口径），中位 9.7% 与 6 批探针的 9.8% 吻合——「143 条下 L3 约 10%」这个量级因此可以当结论用，不再是 6 批噪声。

#### 为什么词库翻了一倍多，中位数只从 13.5% 掉到 ~10%

把残留的生词逐个查库，答案很直接：

- `lex6` 的 19 个不同生词里，**16 个（占出现次数的 90%）本来就在词库里**：`price`(×5)、`ask`(×4)、`try`(×3)、`right`、`strange`、`tiny`、`quiet`、`shop`、`clear`、`wait`、`found`、`begins`、`waits`、`happens`、`clues`、`bags`。它们被判生词不是没登记，而是没过**能力门**：`knownWordSet()` 只收 `ability ≥ 0.6` 的条目，冷启动时几乎全为 0。
- `lex6b` 的 21 个里只有 11 个在库（占出现次数约 57%），另一半是真缺的常用词（`pick`、`great`、`problem`、`correct`、`end`、`delivery`、`deliver`、`crown`、`uses`、`perfectly`）——但每个只出现 1 次，对中位数贡献有限。
- 本批要教的条目（`brief.introduce` / `expose` / `review`）的形式**早就**在允许词表里（`apps/lab/src/data.ts` L175–184，方案第 5.1 节的注释写的就是这条）。所以「多登记条目」根本不会把它们从 OOV 里拿掉——只有「这一批真的教到它」才会。

结论：**L3 的瓶颈是能力门 + 写手对允许词表的遵守度，不是词表长度。** 按这个机制推算，继续把词库堆到方案要求的 300 条也不会压低中位数。真正能动 L3 的只有两条：规划器按频率先教（`introduce` / `expose` 的顺序），或把 `allowed_words` 从上千词的清单改成写手看得懂的短白名单（现在 `allowed_words` 已含 321 个功能词 + 全部已知形式，模型显然读不动这么长的一张表）。

副作用要记一笔：词库与功能词一改，`allowed_words` 就变，写手请求的输入 token 从 ~3.7k 涨到 ~5.4–5.9k（K1 因此上升），响应缓存也全部失效——这次是刻意接受的代价。

#### 量 L3 时发现的两个口径 bug（已修）

测这个数的时候顺手发现指标本身有两处失真，两处都修了，`lex6b` 用的是修好的口径：

1. **低于告警线的批次被当成「没有数据」丢掉**。原来 L3 只能从 `W-OOV` 的文案里正则抠百分比（`pipeline.ts` 的 `oovRatioOf`），于是 OOV < 8% 的批次没有消息可抠，`oovRatio` 记 `null` 后被中位数过滤掉，只剩「超标批次」参与统计，中位数系统性偏高。现在校验器直接回报计数：`ValidateOutput.vocab = { totalTokens, oovTokens, oovRatio }`，流水线读计数，只有失败批次才留 `null`。`lex6` 里的 `b-0004`、`b-0005`（没触发告警）和 `lex6b` 里的 `b-0001`(3.9%)、`b-0006`(7.4%) 就是被这条丢掉的那几批。
2. **多词形式只认相邻两词**，`in front of`、`on the shelf` 这类三词块永远匹配不上（`in`、`of` 本是功能词，会先被单词分支消化，`front` / `shelf` 就剩成生词）；而且匹配时直接改传进来的 `allowedForms`，同一个 ctx 用第二次就丢掉整份多词表。现在按首词建索引、支持任意长度、最长优先，并且只在副本上操作。两处都补了测试（`packages/esl/test/validator.test.ts`）。

`lex6` → `lex6b` 的 12.1% → 9.8% 同时含口径修正与采样噪声，**不作归因**；能确定的是口径修正之前的 L3 数字偏保守（偏高）。

> **回放的边界**：`lab run` 结束时**在同一个进程里**算出 `metrics.json` / `report.md`，这份产物永远和当次运行一致。`lab metrics <run>` 是**重新跑一遍流水线**（读 `runs/<id>/cache` 的响应缓存，不发真实请求），只有当前代码产生的**请求哈希**与该次运行完全一致时才能命中；改动提示词、分阶段输出上限、`hashSalt` 中的任何一项都会让回放全部未命中，指标归零。因此：**运行结束后不要再对它的产物跑 `lab metrics`**，要重算就重跑；`cmdMetrics` 已加保护——回放 0 批通过时保留原 `metrics.json` 并打印警告，不再覆盖。
>
> `smoke-real-20f` 的 `metrics.json` 就吃过这个亏：20g 之前的「分阶段上限合并」修复改掉了 `maxTokensByStage`，20f 的缓存再也命中不了，一次无 key 的 `lab metrics` 把它写成了 0 通过（`cost` 块因沿用旧值仍是原数）。表中 20f 的指标取自运行结束时的输出，`batches/`、`calls.jsonl`、`feedback.jsonl` 原始证据完好。
