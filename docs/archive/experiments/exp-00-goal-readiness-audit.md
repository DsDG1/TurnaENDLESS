## 0. 结论

**功能是齐的，目标是没达成的，而且有两项不是"跑完 R0–R5 就知道"，是结构性障碍。**

分三层说：

1. **功能层：齐备。** 方案第 5 节的组件全部有实现，`pnpm typecheck` 全绿，`pnpm test` **218 项全过**（esl 85 / world 12 / learning 18 / director 35 / lab 68），`lab check` 数据与冻结校验通过（143 条词库 / 86 emoji / 6 背景 / 8 谓词 / 40 梗 / 系统提示词 v14），Stub 5 批端到端冒烟 5/5 通过（23 卡、V2 100%、K5 2.30）。
2. **目标层：10 项阈值里 1 项实达标（L1 100%）、1 项数字达标但空心（C1 0.0%）、2 项不达标（V2 / K4）、2 项不可判定（L4 / K2）、4 项无数据（人工"想看下一张" / N5 / N2 / L5）。** C1 的空心见 2.1：世界库里只有 4 条种子 canon 事实，任何剧情都没法与它冲突。
3. **两项结构性障碍：**
   - **世界状态层在真实产出上完全空转**：20o 的 18 个通过批次里，`effects` 声明数 = 0、`story` 场景数 = 0，`world.sqlite` 里除了 4 条种子 canon 事实之外**一条新事实、一条事件、一条伏笔、一条用户事实都没有**。这意味着按方案跑的 R1–R5（世界状态 开）与 R0（世界状态 关）在真实产出上会是同一个实验，RQ2/H2 无材料可验。
   - **K4 差一个量级**：实测单批生成 P50 58s，而 P1 画像 4 卡/批的消费速度约 20s/批。缓冲模拟的达标边界在 ~9s/批（8s → 0.8% 通过，12s → 13.3% 不通过）。当前是 **97.5% 卡顿**，靠加缓冲（B=1/2/3）与派生填空（每批 1 张）都压不下来（派生只能覆盖 0.14% 的等待）。

按方案 9.2 的三选一：**既不能判"进入 MVP"，也不能判"调整方向"或"停止"——判定条件本身还缺 7 项数据；但可以先判定"当前配置下 H4 与 H7 不成立"。**

### 2.1 C1 的 0.0% 为什么不能当 H2 的证据

`runs/smoke-real-20o/world.sqlite` 的实际内容：

| 表 | 行数 |
|---|---|
| `entities` | 12（种子 + `new_entities`） |
| `facts` | **4（全部 standing=canon，即种子）** |
| `events` | **0** |
| `threads` | **0** |
| `user_facts` | **0** |
| `episode_summaries` | 0 |

对照 Stub 5 批（人手写的 effects）：facts 6（4 canon + 2 stated）、events 7、threads 4、user_facts 1 —— **机制是通的**，是真实产出没有喂进来。

C1 的分母是"提及已知实体的叙述行"（139），分子是 `E-FACT-CONFLICT`。世界库里只有 4 条 canon 事实（鸭子是鸭子、店在某处之类），**任何剧情都没有可能与它冲突**。所以 0.0% 只证明"没写出与种子 canon 冲突的句子"，不能证明"角色记得以前发生过的事"。

## 3. 结构性障碍一：世界状态层没有输入（影响 RQ2/H2，并会让 R1–R5 退化成 R0）

**事实链：**

1. 20o 的 18 个通过批次里，`grep -l effects batches/*.esl.yaml` → **0 个批次**声明过 `effects`；`open_thread` 0 次、`set_fact` 0 次、`user_fact` 0 次、ink 标签 `# effect:` 0 次。
2. 场景类型分布（60 个场景）：comic 17 / chat 16 / pick 11 / swipe 10 / hidden_object 10 / **story 0**。`story` 是唯一能承载 ink 分支与 effects 的场景类型，模型一次都没写。
3. 频道分布：improv 8 / duck_detective 6 / impossible_store 4（设计比例 20/50/30）——20o 跑在 `channel_weights` 接通之前，属于已知偏差，已修但未复测。

**根因（不是模型不听话，是提示词自己把 effects 说成可选项）：**

- `writer.md:132` 写的是"`effects` 里每个名字都必须被引用，没被引用的直接删掉，否则整批被阻断"——只讲怎么删，没讲什么时候必须写。
- `showrunner.md:34` 写的是 `thread_ops: []  # 可选`。
- 提示词里**没有任何一条要求"本批至少要有一次世界状态改变"**；`precheckPlan`（5 项检查：梗重复、序列重复、学习覆盖、防启动、cast 合法 + needs 解析）也没有这一条；校验器没有对应的阻断码。
- 结果：模型选最省事的六种场景里最不容易出错的那五个，世界状态恒为空。

**后果：**

- RQ2/H2（长程一致性）在真实产出上**没有可验证对象**；C2 伏笔卫生恒为空表；C3 回调正确率（`sift` 的 4 个模式全靠 `threads` / `user_facts`）永远不会触发；频道调度的"伏笔压力"项恒为 0。
- R1（单段 + 世界状态）与 R0（单段 + 无世界状态）的差别理论上只有上下文里那几块内容——世界状态空 → **两条运行会产出几乎相同的东西**；R3（梗台账）也会因为"没有 thread 可回调"而削弱。
- 20o 的 18/20 因此**不能当作 R1–R5 的预演**，只能当作 R0 的预演。

**修的落点（三处，都在跑全量之前）：**

1. 提示词加硬规则：「每批至少一次世界状态改变」（`chat.reply.options[].effect` 或 `story` 的 ink 标签都可以承载，不必强制写 story）。
2. `precheckPlan` 增加一条：`thread_ops` 为空且 `beats` 里没有 effect 载体 → 判预检失败并回退重试（方案 5.7.2 允许扩展检查项）。
3. 或者在校验器加建议级 `W-NO-WORLD-CHANGE`，并在 `metrics` 里单列"零 effect 批次占比"，避免下次再靠 grep 才发现。

## 4. 结构性障碍二：K4 差一个量级（影响 H7，且不能靠缓冲或派生解决）

**量级账：**

- P1 画像：4 卡/批 × 单卡停留中位 4s ≈ **20s/批** 的消费速度。
- 实测生成：P50 **58s**/批（20o），P95 126s，69 次调用 / 18 批 = **3.8 次调用/批**。
- 达标边界（`buffer-sim` 扫描，P1 / B=2 / 预制 3）：8s → 0.8% ✅；12s → 13.3% ❌。**边界 ≈ 9s/批**。

也就是说，要满足 H7，需要把单批生成时间从 58s 压到 9s（**6.4 倍**），或者把每批卡数从 4 提到 26 张（同样 6.4 倍吞吐）。当前所有开关都做不到：

| 手段 | 实测效果 |
|---|---|
| 缓冲 B=1/2/3 | 99.2% → 87.5%，只是把首屏等待挪走，稳态仍卡 |
| 预制 3/5 批 | 91.7% / 91.7%，治首屏不治稳态 |
| 派生填空 1 张/批（B3） | 覆盖等待 **0.14%**，等于没有 |
| 并发 2 | `budget.yaml` 现为 1；即便按 2 算也只能把 58s→29s，仍差 3 倍 |

**结论：** H7 在当前"两段式 + 3.8 次调用/批 + 4 卡/批"的形态下不成立。可达的路径只有三条（都要改设计参数，不是改代码）：① 提高 K5（一次调用产出更多卡，方向与第 3 节的"派生"一致，但要 6 倍而不是 25%）；② 单段提示词 + 前缀缓存（省调用次数）；③ 换更快模型或降低思考量。**这条必须在跑 R0–R5 之前定，否则 1080 批跑完也只是一份"卡顿 97%"的报告。**

## 5. 结构性障碍三：V2 的 97% 只剩一条未验证杠杆

- 现状：90%（54/60），单次最佳 95%。
- 剩余失败**全部是"编名字"**：不存在的素材标签（`@tag:apartment`、`@emoji:crate`）、不存在的条目 ID（`lx:mouse#n.rodent` 写进 `uses`）、角色属性越界（`expr=shock`）、自造实体（`mouse` / `detective` / `robot`）。
- 已证伪的两条路：提示词（v9 反例无效、v12 正例只清掉 `@emoji:hat` 两格）、解码期约束（该端点静默忽略 `response_format`，结果文档 §7 第 9 条）。
- 唯一未验证的杠杆：**A2「名字从生成挪到选择」**——`resolveName` 28 条别名 + `available_names` 短清单已进 v14 提示词（`pipeline.ts:539` → `director.ts:573`），但**没有跑过真实 20 批**（本机无 `ENDLESS_API_KEY`）。

**判定：** V2 ≥ 97% 目前是**"可能可达但未证明"**。若 v14 + A2 的 20 批仍停在 90%，则方案 9.1 的"97%"应该走它自己留的口子——「试跑后可调整一次阈值并记录理由」，而不是继续在提示词上耗。这一条建议在跑全量之前先验，因为它决定 R0–R5 跑完后能不能判"进入 MVP"。

## 8. 建议的执行顺序（跑全量之前）

按"不修就会白跑"排序：

1. **给世界状态加输入**（第 3 节三步）。不做这一条，R0–R5 里 5 条开世界状态的运行都会退化成 R0 —— 17–26 小时预算会买回 1 份有效数据 + 5 份复制品。
2. **先跑 20 批 v14 + A2**（第 5 节），把 V2 的天花板量出来。若 < 97%，就地按方案 9.1 的"试跑后调阈值一次"改判，并写清理由；这决定判定表能不能收口。
3. **定 K4 的参数**（第 4 节）：要么接受"K4 不达标、H7 不成立"并写进结论（务实），要么先把形态改成单段 + 并发 2 + 每批 ≥ 12 卡再跑。别带着 97% 的卡顿去跑 1080 批。
4. **补三个工具**：S-R 回放、L4 程序口径、人工评分表聚合（α / ρ）。人工评审是 5 项阈值的唯一来源，现在一件工具都没有。
5. 修文档漂移（第 7 节），特别是 README 的测试数与提示词版本——它是外人看这个项目的第一个门面。

已经可以下的结论不用等全量：**H6 成立（S-B 最优，ECE 0.1934）**、**H4 不成立（90% < 97%，且剩余失败无已知解法）**、**H7 不成立（97.5% ≫ 5%）**。这三条都已有可复现读数。
