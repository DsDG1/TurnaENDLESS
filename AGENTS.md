# Project workflow

- Use Node.js >=22.12 and pnpm 10.29.2. This is a TypeScript workspace.
- `pnpm dev` starts the web app on loopback port 5173 and the local AI API on 4174. `pnpm dev:api` starts only the API.
- `pnpm build` typechecks the API and builds `apps/web`, including its PWA manifest and service worker.
- `apps/desktop` is an Electron Windows x64 test shell, not a signed/installed production release. `pnpm desktop` builds and opens it; `pnpm desktop:package` builds a self-contained application folder under `out/desktop/` (keep the whole folder, not just its exe). Repeated packaging preserves previous folders and uses a timestamped subdirectory; `out/desktop/latest.json` identifies the latest executable. `pnpm desktop:test` runs Playwright against that packaged exe from a temporary working directory, without requiring a system Node.js or the repository at runtime. `pnpm -C apps/desktop test:smoke` instead checks the development runtime after `pnpm desktop:build`.
- Desktop runs its bundled UI and loopback-only API at the fixed origin `http://127.0.0.1:4175`; an occupied port is an error, never a reason to select another origin or attach to an existing service. It is single-instance, sandboxed, has no renderer Node/IPC bridge, and starts/stops the API in an Electron utility process. API initialization/storage failure keeps the bundled reader available with safe 503 API responses and does not reset files.
- Desktop test data lives in `%APPDATA%/ENDLESS-Test/` (IndexedDB plus the separate `api/jobs.json` and `api/edition.sqlite`), independent of browser saves and repository API data; no automatic import/migration is performed. `ENDLESS_DESKTOP_TEST_DATA` is only an explicit test-profile override. Packaging copies built web assets, bundled server code, model selection and lexicon only, never `.env`, keys, local jobs, SQLite files or browser profiles. The page-key lifetime and generation/restart contracts remain unchanged.
- Electron downloads use the published npm package's bundled SHA-256 checksums. If GitHub is unreachable, the current PowerShell process can set `$env:ELECTRON_MIRROR = "https://npmmirror.com/mirrors/electron/"` before running `pnpm -C apps/desktop exec node node_modules/electron/install.js` or packaging; do not disable checksum verification or change dependency security policy. Web/PWA and `packages/*` remain the reusable mobile foundation; Electron and its Node utility process are desktop-only, not an implemented Android/iOS backend.
- `pnpm preview` serves the production build on loopback port 4173 and starts the AI API on 4174. Vite proxies `/api` in both development and preview. Stop previous preview/API processes before restarting to load configuration changes. PWA installation and offline caching must be verified against production preview, not the development server.
- Verification: `pnpm test`, `pnpm typecheck`, `pnpm build`, and `pnpm test:e2e` after building.
- Browser tests use Playwright Chromium by default; install it with `pnpm -C apps/web exec playwright install chromium`. On Windows with Edge installed, PowerShell can use `$env:PLAYWRIGHT_CHANNEL = "msedge"; pnpm test:e2e` instead.
- `packages/player` is a platform-independent, event-replayed player using the existing ESL compiler, learning evidence strategy S-B, FSRS, BKT, and world reducer. Do not replace user interactions with the experiment learner simulator.
- `apps/web` is a single-device PWA with three bundled episodes and manual AI continuation after all current episodes are completed or skipped. Cached/generated episodes work offline; generating requires the local API and connectivity. There are no accounts or synchronization. Never include provider keys or server configuration in the browser bundle.
- `apps/api` reads the existing provider/model selection from `apps/lab/config/models.yaml` without using the experiment pipeline or frozen prompts. Users can enter a MiniMax Key in the web UI: it lives only in the page's React state, clears on reload/full navigation/pagehide, and is never stored in IndexedDB, localStorage, sessionStorage, tickets, exports, URLs, logs, or task records. It is sent only on generation submission in `X-Endless-Provider-Key`, after origin/capability checks, and used by a per-job client in the local API process. It is not a browser-direct provider connection. Polling and restoring a submitted job do not require retaining the Key. Clearing the page Key does not cancel a running server call.
- Optional `ENDLESS_API_KEY` through the API environment or ignored `apps/api/.env` remains a fallback; an explicit page Key takes precedence only for its own job and must not become a server-wide default. Never inspect or print real secret values. Missing credentials must leave offline playback usable. Real-provider verification is separate from synthetic-key/stubbed tests.
- The API is loopback-only, not a public deployment. Keep Host/Origin checks, no-store responses, and the per-process capability header. A public deployment needs authentication, per-user state/quotas, and HTTPS before exposure.
- AI jobs are explicitly user-triggered, persist reservations/results in ignored `apps/api/data.local/jobs.json`, and never automatically replay interrupted or failed provider calls. Limits: one active job and a 200-record job cache (oldest terminal records are evicted automatically; active jobs are never evicted); there is no daily quota, per-job call/token budget, or generated-episode cap. The v4 repair loop is capped at 6 attempts and a 120k-token budget per job, and stops early when the normalized failure signature (digits folded) repeats. AI SDK transport retries are disabled in application mode.
- `packages/content` owns the shared pilot contract, state-derived generation planning, and validation at both server/client boundaries. AI documents retain original batches, hashes, and event-prefix bindings; restore validates against generation-time history, not the later world state. Client acceptance checks every answer/skip path before committing.
- New AI generation uses `learningVersion: 4` and the ENDLESS-DRAFT/1 compact creative protocol (`apps/api/src/creative-prompts.ts`, `packages/content/src/creative-policy.ts` — correctness-critical, do not re-author): the model writes a compact draft of metadata plus component blocks (@comic/@chat/@post/@choice/@quiz/@card/@fact/@example) — never executable JSON — choosing @kind (story/daily/social/knowledge) and @series from the shared catalogue with history-based soft recommendations (no forced sequence or question quotas). `packages/content/src/creative.ts` strictly compiles drafts: program-assigned scene IDs, lexicon references, material refs, deterministic answer positions, evidence, and creation metadata; quiz/card/fact/example bodies are program-constructed from the local lexicon or truly-read prior lines only. A required `creation` binding records protocol/draft/kind/series/sources and is re-compiled and compared on accept/restore, so forged sources, kind/series switches, or tampered text are rejected even with recomputed hashes. Versions 1–3 stay legacy contracts (`plan()` still defaults to 3); stored batches are never upgraded or reinterpreted in place. Scenes 10–20 including exercises for v4; legacy keeps 3–4 base scenes. Each draft component compiles to exactly one scene, so the component count must also stay within 10–20 (the prompt states this; do not reintroduce a 1–10 component cap). Each batch introduces 2–5 new terms or knowledge points (`creativeIntroductionPolicy` in `creative-policy.ts`, rotating 2→5 with episode count); every one of them needs two real narrative contexts plus its own practice interaction, so a 5-term batch spends five of at least ten (10–20) component slots on practice. Teaching/practice never creates an FSRS grade; a required new term still needs two real narrative contexts plus practice (knowledge uses fact+example as its two contexts); card never fulfills a required interaction.
- Vocabulary notes include actual completed-reading exposures as well as answer items, with separate exposed/practice/scheduled states. Undisplayed, skipped, and merely generated content must not count as learned. Showing a planned new word does not change progress. Concretely: an episode counts as read only when every scene advanced without skipping (`episodeCompletion` in `@endless/player`; a skipped scene also advances the cursor, so the cursor alone is not completion), scene `uses` are derived from narrative units only (a target appearing in a distractor, prompt or feedback is not exposure), and archive summaries quote only truly-read episodes (rumor `standing` never becomes a confirmed fact).
- Application generation uses compact task-specific context, mechanical metadata fixes from the ESL package, and whole-batch correction with the prior draft and all constraints. It retains strict vocabulary checks; repair retries are capped at 6 attempts and a 120k-token budget, and also stop early on identical normalized failure signatures. Never drop scenes, invent world choices, or remove required learning tasks to make validation pass. Experiment defaults still use scene-level repair.
- Generation failures expose safe categories/codes and actionable messages (content validation, authentication, rate limits, timeout/network, budget), not provider response bodies, prompts, or keys. Keep the specific failure visible in the generation panel.
- Pilot content is validated before compilation. Legacy writer output (v1–3 path) may contain only comic, chat without Ink, and pick scenes plus program-built exercise cards (quiz/card) excluded from the 3–4 base-scene cap; the v4 draft path instead accepts the eight catalogue components and compiles them into comic/chat/pick/quiz/card scenes. Do not silently discard unsupported scene types or directives. Visual scope is the registered material catalogue only (12 characters, 12 backgrounds, 40 props — original vector art in `apps/web/src/components/art.tsx` and `packages/content/materials/svg/`, green/cream language, offline-bundled); knowledge direction is sourced language/lexicon content (fact/example copy exact lexicon text with a displayed source label), not arbitrary science or UI code, and no audio.
- Application saves use the `endless-workspace` contract (`packages/content/src/application-contract.ts`, `WORKSPACE_SCHEMA_VERSION`): local profile, content entries, revisions, progress branches, obligations, archive volumes, checkpoints and generation tickets, committed in one IndexedDB transaction under `repositoryRevision` CAS (stores: meta/revisions/branches/objects/staging). The old `endless-player` version-1/2 envelopes are not read, not migrated and not dual-written: anything that does not match the current schema must be reported as unsupported and preserved, never silently reset. Pending generation tickets survive refresh and block writes from other tabs until committed or explicitly released.
- Edition (`docs/edition-design.md`, engineering M0–M5 implemented; milestone exits not all reached — see §21.3) is a separate contract (`edition-draft-v1`, header `EDITION-DRAFT/1`) exported as the `edition` namespace from `@endless/content`. It never reuses `learningVersion: 4`: ENDLESS validation rejects Edition documents and vice versa. `pnpm test` covers `edition-core`, `edition-sample` (acceptance matrix C01–C06, L01–L08, P01/P06, Q02–Q04) and `apps/web/test/edition-storage`; `apps/web/e2e/edition.spec.ts` verifies install → read → refresh.
- Edition rules that must not be relaxed to make content pass: approved `own-work`/public-domain/CC0 sources only (`rights-policy-v1`), no `@reading` body from the model, in-unit interactions are `practice` only (graded retrieval lives in the separate review segment), every first-teach target needs two distinct real narrative contexts plus one practice, one `IssueRelease` per issue per CEFR, releases are immutable (corrections are new releases marked superseded/withdrawn), and publication requires all planned units validated plus an approval bound to the current digest.
- Edition storage is the companion IndexedDB `endless-editions` (CAS on `repositoryRevision`, events in chunks, install activated in one transaction). It never parses, migrates or resets `endless-workspace`; an Edition failure must not break ENDLESS offline playback. Reader backups are `edition-backup/1` JSONL containers; unknown trust roots stay quarantined.
- Edition's local API is `apps/api/src/edition/` (SQLite via `node:sqlite`, compile job state machine, protected routes, versioned prompts, deterministic compile runner). Approved unit drafts are registered through the protected `POST /api/editions/:id/drafts` route (`putDraftUnit`), after which `compile_issue` re-compiles and verifies them deterministically; `edition-status` reports `capabilities.draftRegistration = true` and still `research`/`fetch` as `library-only`. Research (`research.ts`) and the safe fetcher (`fetch-source.ts` + `node-fetch.ts`) remain library-level only: they have tests but no HTTP route or UI yet. It shares only the execution gate with ENDLESS; the gate is **strictly exclusive** (a second task of the same mode is also rejected, and Edition checks it at submit instead of creating a doomed job), so the two modes never call a provider concurrently. SQLite sets `busy_timeout`, and an externally held write lock surfaces as `503 E-EDITION-BUSY` instead of a generic outage. Reader backup import only trusts locally known roots (`local`); a container's self-declared `trustRoot` is never evidence. It never reads or rewrites `jobs.json` or `endless-workspace`. Job invariants: persist `reserved` before any provider call, persist `result_saved` before the next unit, same `requestId` + different `taskDigest` is 409, one open attempt per `workKey`, restart marks `queued/running` interrupted, `cancel_requested` cancelled, and `call_started` attempts `unknown` without replaying them; a plan approval whose digest no longer matches the current editorial revision is rejected at submit.
- The safe fetcher must keep rejecting IP literals, private/reserved DNS answers, non-443 ports, non-allowlisted hosts, untrusted content types, oversized/compressed responses and over-limit redirects, and must pin each hop to the validated address while keeping the original Host/SNI. Fetched text is untrusted data: injection phrases are recorded, never executed, and the model still has no fetch tool.
- Still not implemented and must not be implied by UI copy: model-driven passage/unit generation (only the `EditorialModel` interface exists), HTTP routes or screens for research and source fetching, the research/plan/review web screens, reader states for not-generated/not-installed issues, a real third-party search provider, automatic plan/passage construction from a corpus, CEFR levels above B1, cross-mode evidence sharing, and external human sign-off for level calibration.

Server-side learning replay arrived only as the later C4 checkpoint service, which has no HTTP route. C3 second round wires the reader: `#cloud-read/<deploymentId>/<accountId>/<workspaceId>[/home|watch|progress]` derives the IDB namespace from all three ids (no "last opened copy" pointer that can dangle), `App` is a thin route shell that remounts `StoryApp` keyed by namespace so guest and cloud states cannot leak into each other, and `usePlayer` opens a cloud copy only when the repository holds **both** a workspace and an installation record (otherwise it fails honestly and creates nothing). While a sync writes the repository, local commits wait for it rather than racing the CAS. - C3 third round adds `0006_sync_forks.sql` (migration level 6) and `POST /sync/streams`. `sync_streams` gains `parent_stream_id`/`fork_at_seq` under a paired constraint (one without the other is rejected), no self-parenting, and a composite FK back to the parent stream. Registration accepts only "parent stream + fork point": the parent must exist, the fork point may not exceed the parent's cloud history, and the server copies `stream_events` membership up to that point (creating the empty stream head first — the FK requires that order) while event bodies stay unique in `event_objects`. Re-registering the same `streamId` is idempotent; different fork parameters return 400 instead of silently rebinding. The browser driver registers any stream that has pending outbox entries but no cloud binding, using the local branch's `parentBranchId` + `forkAtEventCount`; it does **not** send a request when the parent's confirmed prefix does not yet cover the fork point (next round trip picks it up) and it never invents a prefix for a root branch with no parent record. Blocked streams leave their events in the outbox and the sync report names the reason instead of only showing a pending count. The server still rejects pushes to unregistered streams with `UNSUPPORTED_CONTRACT` and keeps the events. Conflict resolution still accepts only `discard`; "keep as an independent branch" needs local branch surgery (new branch carrying the local history, parent branch reset to the cloud prefix, old stream's pending entries dropped) and is not implemented. See `docs/cloud-baseline.md` §9.5.
- C3 fourth round supersedes the earlier discard-only statements: `0007_sync_conflict_preservation.sql` (required migration level 7) adds branch manifests and digest-bound preservation receipts. `keep-branch` creates an independent root, shares only common-prefix event membership, and atomically records the result; it never reuses revision-edit fork semantics.
