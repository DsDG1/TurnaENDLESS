# Real cloud reader browser acceptance

Run `pnpm -C apps/api test:cloud:browser` from the repository root. This first runs `pnpm build:cloud`, producing the explicit cloud PWA in `apps/web/dist-cloud`, then runs two complete journeys with real cloud HTTP routes and a disposable PostgreSQL cluster. The fixture checks the build profile and never serves the default local `apps/web/dist` build. Install Playwright Chromium first (`pnpm -C apps/api exec playwright install chromium`), or set `PLAYWRIGHT_CHANNEL=msedge` on Windows. Missing infrastructure fails the suite; these journeys are separate from the default unit tests.

Each journey uses two isolated browser contexts, one desktop and one mobile viewport. Only the initial guest workspace is seeded directly. Login, import, claim, reading, offline conflict resolution, display edits, revision adoption, archives, lifecycle, pause, session expiry and account isolation use the production UI and API. Lost responses are injected after the real server has returned; retries must recover the persisted result. The fixture then prunes the reading change journal in its disposable PostgreSQL cluster, advances its retention watermark and epoch, and checks snapshot recovery with every immutable event and identity retained. An additional fresh device claims the same pruned workspace and installs the missing revision registrations through native reconstruction. This does not enable or validate an automatic production pruning policy.

SMTP delivery uses the real encrypted mail outbox and MailWorker with a loopback TLS SMTP fixture. Object operations use the real S3 client against a loopback SigV4-checking fixture. These are not real provider or deployment acceptance. Synthetic OTP timestamps are advanced between deliberate logins to avoid waiting through the resend interval; authentication still consumes real single-use challenges.

Each journey receives its own disposable PostgreSQL cluster and browser. This keeps extra renewal/fresh-device logins from consuming another case's persisted IP quota; production rate limits are unchanged.

The generated episode is genuinely completed before revision preview/adoption. The journey verifies that its obligation stays fulfilled, the original device's completion time remains intact, and both an existing peer and a fresh installation rebuild the adoption-time inventory. Archive assertions wait for the real applied HTTP receipt and the subsequent atomic browser commit; they are correctness checks, not target-device performance thresholds.

The same-origin HTTPS gateway serves an immutable snapshot of the actual production assets. Its certificate is temporary and trusted only by these browser contexts. A context-scoped asset relay fetches the same bytes through the context's certificate exception because Chromium's service-worker loader does not inherit the page exception. `/api/*` always passes through to the real server; the relay never supplies cloud business responses. Offline asset misses fail, so the cold reload exercises the actual service-worker cache. No system trust or global TLS settings change.

Failure screenshots go to a unique `out/cloud-browser-*` directory. Do not rebuild `dist-cloud` while a cloud preview is serving it; local builds and previews use the separate `dist` directory. Do not deploy the two profiles at the same origin concurrently: their existing PWA identity and scope remain unchanged. No production credentials, real mail, model calls, payments or user data are used.
